## 1. 产品概述

### 1.1 背景与问题

建筑学领域的信息检索存在两个长期痛点：

1. **规范条文关联紧密、难以精准定位**：规范条款互相引用（如“按第 X 条执行”），上下文依赖强，传统关键词搜索难以精准定位真正相关的条款。
2. **文献查阅效率低**：学术研究与设计实践需要反复查阅特定方向的文献和规范，但每次都要在 PDF 中手动翻找，效率极低。

### 1.2 产品定位

**ArchMind 是一款面向建筑规范、文献与案例资料的 AI 知识检索与案例分析助手。** 用户上传自有资料后，可用自然语言提问，系统通过 RAG（检索增强生成）返回有来源可核验的回答；并可基于资料生成结构化的案例分析报告。

### 1.3 产品目标

| 目标 | 说明 |
|---|---|
| 短期（v1.0） | 验证 RAG 技术链路：上传 → 切分 → 向量化 → 检索 → 生成 → 来源展示，跑通多格式文档与多模型服务 |
| 中期（v2.0） | 从“单次问答”扩展为“案例分析工作流”：资料上传 → 用途/维度选择 → 结构化报告 → 汇报提纲 → 导出保存 |
| 长期 | 建立评测闭环与条款级引用能力，成为建筑从业者可依赖的私有知识库问答工具 |

### 1.4 成功指标（定义方法，暂不填数值）

- **检索命中率**：固定题集中 Top-1 / Top-4 找回正确资料的比例（已有 v1 评测基线）。
- **证据完整性**：回答是否保留必要条件和限制。
- **引用准确性**：来源是否真实支持对应结论。
- **无依据回答率**：资料库无答案时是否明确拒答而非编造。
- **任务完成率**（v2.0）：用户从上传到导出报告的完整流程完成比例。
- 以上指标全部来自项目自建评测，**不以用户数、访谈人数、节省时间比例等未验证数据对外宣称**。

## 2. 目标用户与使用场景

### 2.1 目标用户（MVP 聚焦）

| 用户 | 典型任务 | 优先级 |
|---|---|---|
| 建筑学研究生 | 课程汇报、论文研究、规范查阅，需要快速定位资料并保留可核验依据 | P0 |
| 设计师助理 | 查规范、做方案对比，需要快速确认“某条件下应满足什么要求” | P1 |
| 建筑从业者 | 把私有知识库转成可检索问答工具 | P2 |

> 暂不同时服务设计院全量用户与所有私有知识库场景，避免 MVP 目标过宽（见《产品验证与优化计划》）。

### 2.2 核心使用场景（v2.0 提炼的 4 个高频场景）

1. **课程汇报**：上传设计资料 → 生成汇报用结构化分析与提纲。
2. **论文分析**：上传文献/案例 → 按论文分析维度输出摘要与来源。
3. **作品集图注**：上传图纸/图片 → 生成图注与设计策略说明。
4. **设计策略清单**：上传规范/案例 → 输出可执行的设计策略要点。

## 3. 竞品与差异化

### 3.1 竞品参照

建筑领域知识检索的替代方案：通用搜索引擎（关键词噪音大、无法溯源）、通用 AI 对话（无私有资料上下文、可能编造条款）、传统规范库检索（只查条文、不做跨文档分析）。

### 3.2 差异化要点

- **私有资料 + 自然语言提问**：针对用户自有规范、文献、案例，而非公开互联网。
- **来源可核验**：回答附带检索来源片段，降低核验成本。
- **场景化输出**（v2.0）：同一份资料按“课程汇报 / 论文分析 / 作品集图注 / 设计策略”产出不同结构的报告。
- **诚实边界**：资料不足时明确说明，不虚构条款。

> 竞品分析已补齐，见 [01-需求调研/竞品分析.md](../01-需求调研/竞品分析.md)。

## 5. 用户流程与信息架构

### 5.1 v1.0 核心流程

```text
上传 TXT / MD / PDF
        ↓
读取并切分文档
        ↓
Embedding 向量化
        ↓
ChromaDB 建立索引
        ↓
自然语言提问
        ↓
检索相关片段（Top-k）
        ↓
Groq / Gemini / Ollama 生成回答
        ↓
展示回答与来源片段
```

### 5.2 v2.0 案例分析工作流

```text
首页 → 资料上传 → 用途与维度选择 → AI 分析结果 → 汇报提纲生成 → 导出 / 保存案例
  │      （文本/图纸）   （4场景+维度）   （结构化报告）      （提纲）      （文件+案例库）
```

### 5.3 信息架构（v2.0 页面清单）

| 页面 | 核心内容 |
|---|---|
| 首页 | 产品入口、新建案例、我的案例库入口 |
| 上传页 | 上传文本资料（TXT/MD/PDF）或图纸图片；展示解析状态、整体进度、已识别的基础信息 |
| 维度选择页 | 选择输出用途（课程汇报/论文分析/作品集图注/设计策略），勾选默认维度，可填写自定义维度 |
| 分析报告页 | 基础信息、总体摘要、分维度分析、来源标注、置信度备注 |
| 提纲/导出页 | 汇报提纲生成，导出文件，保存到“我的案例库” |

### 8.4 关键产品决策记录（ADR）

| 决策 | 理由 |
|---|---|
| 不直接导入规范全集 | 相似术语、重复条款、目录附注会稀释检索精度；条文上下文依赖（“按第 X 条执行”）在 chunk 切割后易丢失；扫描 PDF 排版解析不稳定。先小批量高质量验证，再扩充 |
| 用 Streamlit 而非自建前端 | 阶段目标是验证 RAG 链路，纯 Python 快速搭建 UI，节省前端开发成本 |
| 用 ChromaDB 而非 Pinecone | 开源、本地、零成本，适合原型；数据规模/并发/权限提升后再迁移 |
| 默认哈希向量 | 零依赖、云演示稳定；语义向量作为可选增强（已列入对比实验） |

## 9. 评测与指标体系

### 9.1 RAG 评测（已有 v1 基线）

- **题集**：20 题，四类各 5 题——直接查找、条件判断、跨段理解、无答案。
- **v1 结果**（基于 `04-测试验证/outputs/ArchMind_RAG_评测结果_v1.md`）：

| 题型 | 题数 | Top-1 找回 | Top-4 找回 |
|---|---:|---:|---:|
| 直接查找 | 5 | 100% | 100% |
| 条件判断 | 5 | 100% | 100% |
| 跨段理解 | 5 | 80% | 100% |
| 有答案合计 | 15 | 93.3% | 100% |
| 无答案 | 5 | 全部低于 0.30 阈值 | — |

- **已确认**：检索配置在当前固定题集上稳定找回正确资料。
- **未确认**：最终回答准确率、引用准确率、不同模型生成质量（受外部模型服务影响，未混入检索评测）。
- **Badcase**：跨段理解题 X04 受相近术语干扰未进 Top-1 → 下一轮引入语义向量与重排对照。

### 9.2 评测方法（持续执行）

每次只改变一个变量（chunk 大小 / overlap / top_k / 向量方式 / Prompt），用同一套题集对比；为每题补充标准证据片段，评测“回答是否保留必要条件”。

### 9.3 用户验证（待执行）

- 访谈模板：目标用户最近一次查规范/文献的任务、工具、耗时环节、可信判断方式、对 AI 证据的期望。
- 体验任务：上传建索引 → 查有答案问题 → 查无答案问题；记录卡点、来源查看行为、可信度判断。

## 11. 风险与依赖

| 风险/依赖 | 影响 | 应对 |
|---|---|---|
| 检索噪音（相近术语干扰） | 跨段理解题 Top-1 命中率下降 | 语义向量对照、重排、chunk 参数实验 |
| 外部模型服务不稳定/额度限制 | 回答生成失败或不可用 | 多服务切换（Groq/Gemini/Ollama）、错误提示明确 |
| PDF 解析质量不稳定 | 索引质量受损 | MVP 优先 TXT/要点摘要，PDF 按需人工校验 |
| 幻觉与无依据生成 | 用户信任受损 | 拒答阈值（当前候选 0.30）、来源强制展示、置信度标注 |
| 免费档休眠/配额 | 线上体验中断 | 明确说明唤醒机制；保留 GitHub Pages 静态 Demo 兜底 |
| 私有资料版权与合规 | 法律风险 | 用户自主上传、不公开传播第三方受版权资料 |

| 术语 | 说明 |
|---|---|
| RAG | 检索增强生成：先检索相关片段，再让模型基于片段生成回答 |
| Embedding | 文本向量化，用于语义相似度检索 |
| Chunk | 文档切分片段，chunk_size 为片段长度，overlap 为相邻片段重叠 |
| Top-k | 检索返回的相关片段数量 |
| ChromaDB | 开源本地向量数据库 |
| MoSCoW | 优先级方法：Must/Should/Could/Won't |
